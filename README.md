Я рассказываю тебе про новую структуру vpn сервиса, прежде чем начать изучать ее изучи: последний релиз панели Remnawave (репозиторий remnawave/panel и контракт API из remnawave/python-sdk). 

Структура сервиса:
Стек:
1)сервера на ubuntu 26.04(1 core, 2gb ram, 30gb nvme)
-ноды за пределами рф
-головной сервер тоже + защита cdn cloudflare
2)панель Remnawave (одна на весь сервис) + remnawave-node на каждой ноде
3)postgresql для бд
3)андроид приложение 
4)реклама рся
5)бот в тг

Алгоритм сервиса:
1)Пользователь скачивает андроид приложение, дизайн мы обсуждали, где чтобы подключиться к впн требуется посмотреть рекламу(15мин подключения - 1 короткая реклама, 1ч - 1 длинная без возможности перемотки), либо платная подписка, платная подписка оплачивается через бота в тг с помощью криптовалюты, если пользователь хочет купить подписку ему всплывает выбор: если у него тг работает идет перенаправление его на бота, если не работает за короткую рекламу дается 15мин впн чтобы он смог зайти в тг и оплатить подписку.
2)Два варианта: первый: пользователь посмотрел рекламу, приложение отправляет на главный сервер информацию, дальше ему в приложение отправляется конфиг и он может подключиться к впн на время, которое соответствует просмотренной рекламе.
Второй: Пользователь решил оплатить подписку, купил ее через крипту в боте и далее бот в тг отправляет информацию о совершенной покупке на главный сервер, и сервер выдает конфиг прямо в приложение.
Для оплаты подписки необходима верификация через тг
3)Сервер все данные о подписках и тд пишет в базу данных

Работа нод:
1)На нодах может быть только vless + reality + xtls на транспорте tcp(только 443 порт), либо grpc(любой порт из незанятых). 
2)Когда нужно создать пользователя создается не инбаунд, а пользователь в панели, привязанный к squad нужной ноды. Инбаунд у ноды один, его настраивает главный сервер

Работа Главного сервера: 
1)Настраивать с нуля ноды, делать инбаунды(автоматически находить хороший sni), добавлять клиентов на ноды
2)Выравнивать трафик, чтобы ноды были одинаково нагружены
3)Следить за нодами, в случае чего отправлять уведомление о настабильной работе нод
4)Стабильно держать всю бд
5)Пооверять просмотр рекламы и оплату подписок
6)По запросу админа предоставлять статистику или менять настройки на нодах

Работа тг бота:
Вариант пользователя:
1)Оплата подписки
2)Поддержка

Вариант админа:
1)Возможность просматривать статистику всех нод
2)возможность добавлять новые ноды и для настройки(вписывать ip, пароль), смена пароля. И удалять ноды.
3)принимать аллерты от главного сервера с информацией где проблема
4)Изменять параметры нод(смена сни, админ нажимает кнопку и главный сервер проверяет рабочие варианты сни для конкретной ноды и устанавливает его)
5)Сообщения из поддержки
6)Возможность переброса пользователей с одной ноды на другую
7)Возможность менять цену подписки и возможность менять время за рекламу, ее количество и тип(с возможностью перемотки и без)
8)Возможность привязывать данные для оплаты в крипте через тг
9)Возможность получать админские конфиги для впн, и чтобы можно было выбирать сервер 

Функционал андроид приложения
1)Кнопка подключить впн
После нажатия выпадает иконка с выбором времени на которое нужен впн
2)У пользователя нет доступа к выбору сервера и страны, он этого не видит
3)Кнопка впн не работает
После нажатия на главный сервер бд выдает другой конфиг, и записывать эту информацию в логи, при накоплении определенного количества таких нажатий на  одной ноде высвечивается аллерт, этот порог срабатывания можно 
настроить через админку в тг
4)Кнопка подписки
После нажатия высвечивается окно, где показывается актуальная сверенная с главным сервером цена подписки, а также что пользователю нужно авторизироваться через тг, он там должен ответить работает или не работает у него тг, если не работает, появляется кнопка посмотреть рекламу за 15 минут бесплатного доступа, после просмотра его просят включить впн и перейти в тг бота, после включения впн его переброс в тг, сначала он авторизируется, потом ему предлагается вариант подписки и инструкция по оплате.

# Архитектура на Remnawave

Проект переведён с 3x-ui на Remnawave. Главное отличие, из которого следует
всё остальное: **3x-ui — это панель на каждой VPS, Remnawave — одна панель на
весь сервис**. Поэтому у нод больше нет своих логинов и паролей, а в `.env`
появился один адрес панели и один токен.

## Как что называется

| Наше понятие | В Remnawave |
|---|---|
| нода | node — VPS с контейнером `remnanode`, которому панель раздаёт конфиг |
| инбаунд ноды | inbound внутри **config profile** (Xray-конфиг, лежит в панели) |
| клиент | **user** — человек с сроком действия и подпиской, а не пара «инбаунд + UUID» |
| «сервер выбирает ноду» | **internal squad** — по одному на ноду |

Про последнюю строку стоит сказать отдельно. У пользователя Remnawave доступ —
это объединение его squad'ов, и подписка отдаёт приложению **все** ноды из них,
а выбирает уже приложение. Здесь выбирает сервер, поэтому каждой ноде даётся
свой squad, а пользователь кладётся ровно в один — тот, который выбрал
балансировщик. Перенос пользователя между нодами — это смена squad'а, с тем же
пользователем, той же подпиской и тем же остатком времени.

## Что нужно настроить

В `.env`:

```
REMNAWAVE_BASE_URL=http://remnawave:3000   # или URL вашей панели
REMNAWAVE_TOKEN=...                        # панель -> Settings -> API Tokens
REMNAWAVE_PANEL_ADDRESS=<публичный IP этого сервера>
REMNAWAVE_NODE_PORT=2222
```

`REMNAWAVE_PANEL_ADDRESS` — не косметика: именно под этот адрес на ноде
пишется правило фаервола для `NODE_PORT`. Если его не задать, порт останется
закрытым, и нода не подключится к панели. Это сделано намеренно: нода, до
которой панель не достучалась, падает громко, а открытый наружу управляющий
порт — нет.

Панель можно поднять здесь же:

```
docker compose --profile remnawave up -d
```

Она публикуется только на `127.0.0.1:3000` — админку нельзя выставлять в
интернет голым портом, ставьте её за тот же реверс-прокси, что и главный
сервер.

## Установка ноды

Всё как раньше: в боте «Ноды → Добавить», ввести IP и SSH-пароль. Дальше
воркер сам поставит Docker, поднимет контейнер `remnanode`, соберёт config
profile с REALITY-инбаундом (SNI подбирается замером с самой ноды),
зарегистрирует ноду в панели и **дождётся, пока панель отчитается, что нода
подключена**. Пока этого не произошло, нода не считается активной и
балансировщик её не выбирает.

## Чего Remnawave не умеет

API панели не отдаёт лог xray с ноды — он лежит в контейнере на самой ноде.
Кнопка «Состояние в панели» показывает то, что панель знает (подключена,
версии, кто онлайн, последнее сообщение об ошибке), а за самим логом нужно
идти на ноду:

```
cd /opt/remnanode && docker compose logs --tail 200
```
