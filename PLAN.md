# План разработки VPN-сервиса (на основе README.md)

Документ описывает архитектуру, разбивку на этапы и открытые вопросы по проекту,
описанному в README.md. Составлен после изучения README и релиза
[`v3.6.0`](https://github.com/MHSanaei/3x-ui/releases/tag/v3.6.0) репозитория
[MHSanaei/3x-ui](https://github.com/MHSanaei/3x-ui) (xray-core v26.7.28,
30.07.2026).

## 0. Что важно в 3x-ui v3.6.0 для нашей архитектуры

Из README следует, что «Главный сервер» управляет нодами через 3x-ui без участия
человека (создаёт инбаунды, клиентов, следит за стабильностью). Актуальный релиз
даёт для этого готовые примитивы — их стоит использовать вместо самописных:

- **REST API инбаундов/клиентов** — создание не инбаунда, а клиента к существующему
  инбаунду (ровно как требует README, п. «Работа нод», пункт 2).
- **Node API токены стали write-only** — токен ноды отдаётся один раз при создании
  и не возвращается повторно. Значит, главный сервер обязан сохранить его в БД
  сразу при регистрации ноды — это нужно заложить в схему БД и в flow
  добавления ноды из тг-бота.
- **Поиск клиента по Telegram ID** (новый GET-эндпоинт) — закрывает требование
  «верификация оплаты через тг»: связку `client ↔ tg_id` можно проверять напрямую
  через 3x-ui API, не дублируя логику на своей стороне.
- **`?format=info` (live online status)** и **порог последовательных сбоев для
  алертов `outbound.down`** — готовая база для требования «следить за нодами,
  отправлять уведомление о нестабильной работе», включая «порог срабатывания
  можно настроить через админку в тг» (README, Функционал тг-бота, п.3).
- **`openapi.json` теперь требует авторизованную сессию** — главный сервер должен
  логиниться в панель ноды (сессионная кука), простого API-токена для part
  вызовов может быть недостаточно — надо на этапе R&D проверить, какие эндпоинты
  требуют сессию, а какие — API-токен.
- Поддержка **VLESS + REALITY + XTLS** (vision flow) и **gRPC** подтверждена и
  актуальна в этом релизе — технически README реализуем на текущей версии 3x-ui
  без форка.

## 1. Архитектура (компоненты)

```
Android-приложение ──HTTPS──▶ Главный сервер (API + оркестрация) ──▶ PostgreSQL
        │                              │      │
        │                              │      └──HTTPS/3x-ui API──▶ Ноды (3x-ui + xray-core)
        │                              │
        └──deep link/redirect──▶ Telegram-бот ──▶ Главный сервер (webhook/API)
                                        │
                                  Оплата (крипта) + Поддержка + Админка
```

Компоненты:
1. **Ноды** — Ubuntu 26.04, 1 CPU/2GB/30GB NVMe, 3x-ui + xray-core, только
   VLESS+REALITY+XTLS (tcp/443 или grpc/любой свободный порт). Никакой прямой
   публичной админки — только API/сессия от главного сервера.
2. **Главный сервер** — тоже за Cloudflare CDN. Отвечает за:
   - первичную настройку нод «с нуля» (установка/апдейт 3x-ui, создание
     инбаунда, автоподбор рабочего SNI);
   - создание клиентов на нодах (не инбаундов);
   - балансировку трафика/нагрузки между нодами;
   - мониторинг нод (heartbeat, alert-пороги) и уведомления в тг-бота;
   - хранение состояния в PostgreSQL;
   - проверку факта просмотра рекламы и факта оплаты подписки;
   - REST API для Android-приложения и для тг-бота (внутренний, авторизованный).
3. **PostgreSQL** — единый источник правды: пользователи, ноды, инбаунды/клиенты
   (зеркало состояния 3x-ui), подписки, платежи, просмотры рекламы, алерты,
   настройки (цена подписки, длительности за рекламу, пороги алертов).
4. **Android-приложение** — простой UI (одна кнопка «подключить», выбор времени
   через рекламу или подписку), без выбора сервера/страны, интеграция с
   VPN-конфигом (VLESS URI) и с рекламным SDK (РСЯ, rewarded video).
5. **Telegram-бот** — два режима (пользователь/админ), оплата в крипте,
   поддержка, полная админка нод и параметров сервиса без доступа к серверу
   напрямую.

## 2. Этапы разработки

**Этап 0 — R&D и контракты API (перед кодом)**
- Поднять тестовый стенд: 1 нода (3x-ui) + локальный вызов API, проверить
  какие операции требуют сессионную куку, а какие — Bearer/API-токен.
  Здесь стоит уточнить: авторизация 3x-ui — по логину/паролю панели.
- Зафиксировать формат конфигурации, которую получает клиент (VLESS URI/JSON),
  чтобы Android-приложение и главный сервер использовали единый контракт.
- Спроектировать схему PostgreSQL (users, subscriptions, nodes, node_credentials,
  clients, ad_views, payments, alerts, settings, admin_audit_log).

**Этап 1 — Главный сервер: ядро + управление нодами**
- CRUD нод (добавление/удаление/смена пароля — из тг-админки).
- Автонастройка ноды с нуля: установка 3x-ui, создание инбаунда, автоподбор SNI
  (проверка нескольких кандидатов на «рабочесть» через тестовое подключение).
- Создание/удаление клиентов на существующем инбаунде.
- Функция ручной/автоматической смены SNI по кнопке из тг-бота.

**Этап 2 — Мониторинг и балансировка**
- Heartbeat/health-check нод (использовать `?format=info` и таймауты).
- Alerting с настраиваемым порогом (используя consecutive-failure threshold
  из 3x-ui) → уведомление в тг-бот админу.
- Балансировщик: при выдаче нового клиента — выбор наименее нагруженной ноды.
- Функция переброса пользователя с одной ноды на другую (миграция клиента).

**Этап 3 — Telegram-бот, MVP**
- Пользовательская часть: авторизация, оплата подписки в крипте, поддержка.
- Админ-часть: ноды (добавление/список/статистика/удаление/смена пароля),
  алерты, смена SNI, переброс пользователей, изменение цены/параметров рекламы,
  выдача админских VPN-конфигов с выбором сервера.
- Интеграция с криптоплатёжным провайдером (см. открытые вопросы).

**Этап 4 — Android-приложение, MVP**
- Экран подключения (кнопка + выбор времени по рекламе).
- Интеграция rewarded-ad SDK (РСЯ): короткая (15 мин) / длинная без перемотки (1ч).
- Экран подписки: сверка цены с главным сервером, флоу авторизации через
  Telegram (deep link + callback), fallback-флоу «нет тг → 15 мин по рекламе → тг».
- Обработка «кнопка VPN не работает»: логирование неудачных попыток подключения,
  запрос альтернативного конфига у главного сервера.
- Локальный VPN-клиент: интеграция xray-core/v2ray core под Android (например,
  через существующие open-source VLESS/Reality Android клиенты как базу) —
  требует отдельного решения по SDK/библиотеке (см. вопросы).

**Этап 5 — Реклама и монетизация**
- Интеграция с рекламной сетью (РСЯ/Yandex Mobile Ads) — rewarded video.
- Учёт просмотров рекламы на сервере (защита от подмены/повторной отправки
  одного и того же ad-impression).
- Логика начисления времени VPN за просмотр.

**Этап 6 — Оплата и верификация через Telegram**
- Флоу «работает/не работает тг» на стороне приложения.
- Криптоплатежи в боте, подтверждение оплаты → callback на главный сервер →
  выдача конфига.
- Anti-fraud: защита от повторного использования одного платежа/webhook.

**Этап 7 — Безопасность и отказоустойчивость**
- mTLS или подписанные запросы между Android/ботом и главным сервером.
- Ротация паролей/токенов нод, аудит действий админа.
- Резервное копирование PostgreSQL, план восстановления нод.
- Rate-limiting и защита API главного сервера (за Cloudflare).

**Этап 8 — Тестирование и запуск**
- Нагрузочное тестирование балансировки трафика.
- Пилотный запуск на 2–3 нодах, мониторинг реальных алертов.
- Постепенный вывод в прод.

## 3. Технологический стек (предложение, требует подтверждения)

- Главный сервер: Go или Python (FastAPI) — оба хорошо ложатся на
  REST-оркестрацию 3x-ui API; нужно решение заказчика (см. открытые вопросы).
- БД: PostgreSQL (задано в README) + миграции (goose/alembic в зависимости от
  языка).
- Тг-бот: aiogram (Python) или отдельный сервис на том же языке, что и главный
  сервер, для переиспользования клиента к внутреннему API.
- Android: Kotlin, интеграция xray-core через существующие Android VLESS/Reality
  библиотеки (например AndroidLibXrayLite или аналог) — нужно выбрать конкретную
  библиотеку.
- Мониторинг: Prometheus/Grafana или встроенные метрики + алерты в тг.

## 5. Риски

- Автоподбор «рабочего» SNI для REALITY нестабилен во времени (блокировки
  провайдеров меняются) — нужен регулярный фоновый ре-чек, а не разовая проверка.
- 3x-ui `openapi.json` теперь требует сессию — обновления библиотеки/API 3x-ui
  могут внезапно ломать интеграцию главного сервера, нужен pin версии + CI-тест
  на реальном стенде при апдейте нод.
- Anti-fraud для рекламы и крипто-оплаты — обязательное условие, иначе сервис
  легко эксплуатировать (бесконечный VPN без оплаты).
- 2GB RAM на ноде — ограничение по количеству одновременных клиентов/трафика,
  нужно заложить лимиты в балансировщик заранее.
