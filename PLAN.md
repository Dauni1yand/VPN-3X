# План разработки VPN-сервиса (на основе README.md)

Документ описывает архитектуру, разбивку на этапы и открытые вопросы по проекту,
описанному в README.md. Составлен после изучения README и релиза
[`v3.6.0`](https://github.com/MHSanaei/3x-ui/releases/tag/v3.6.0) репозитория
[MHSanaei/3x-ui](https://github.com/MHSanaei/3x-ui) (xray-core v26.7.28,
30.07.2026).

## 0. Что важно в 3x-ui v3.6.0 для нашей архитектуры

Из README следует, что «Главный сервер» управляет нодами через 3x-ui без участия
человека (создаёт инбаунды, клиентов, следит за стабильностью). Актуальный релиз
даёт для этого готовые примитивы — их стоит использовать вместо самописных:

- **REST API инбаундов/клиентов** — создание не инбаунда, а клиента к существующему
  инбаунду (ровно как требует README, п. «Работа нод», пункт 2).
- **Node API токены стали write-only** — токен ноды отдаётся один раз при создании
  и не возвращается повторно. Значит, главный сервер обязан сохранить его в БД
  сразу при регистрации ноды — это нужно заложить в схему БД и в flow
  добавления ноды из тг-бота.
- **Поиск клиента по Telegram ID** (новый GET-эндпоинт) — закрывает требование
  «верификация оплаты через тг»: связку `client ↔ tg_id` можно проверять напрямую
  через 3x-ui API, не дублируя логику на своей стороне.
- **`?format=info` (live online status)** и **порог последовательных сбоев для
  алертов `outbound.down`** — готовая база для требования «следить за нодами,
  отправлять уведомление о нестабильной работе», включая «порог срабатывания
  можно настроить через админку в тг» (README, Функционал тг-бота, п.3).
- **`openapi.json` теперь требует авторизованную сессию** — главный сервер должен
  логиниться в панель ноды (сессионная кука), простого API-токена для part
  вызовов может быть недостаточно — надо на этапе R&D проверить, какие эндпоинты
  требуют сессию, а какие — API-токен.
- Поддержка **VLESS + REALITY + XTLS** (vision flow) и **gRPC** подтверждена и
  актуальна в этом релизе — технически README реализуем на текущей версии 3x-ui
  без форка.

## 1. Архитектура (компоненты)

```
Android-приложение ──HTTPS──▶ Главный сервер (API + оркестрация) ──▶ PostgreSQL
        │                              │      │
        │                              │      └──HTTPS/3x-ui API──▶ Ноды (3x-ui + xray-core)
        │                              │
        └──deep link/redirect──▶ Telegram-бот ──▶ Главный сервер (webhook/API)
                                        │
                                  Оплата (крипта) + Поддержка + Админка
```

Компоненты:
1. **Ноды** — Ubuntu 26.04, 1 CPU/2GB/30GB NVMe, 3x-ui + xray-core, только
   VLESS+REALITY+XTLS (tcp/443 или grpc/любой свободный порт). Никакой прямой
   публичной админки — только API/сессия от главного сервера.
2. **Главный сервер** — тоже за Cloudflare CDN. Отвечает за:
   - первичную настройку нод «с нуля» (установка/апдейт 3x-ui, создание
     инбаунда, автоподбор рабочего SNI);
   - создание клиентов на нодах (не инбаундов);
   - балансировку трафика/нагрузки между нодами;
   - мониторинг нод (heartbeat, alert-пороги) и уведомления в тг-бота;
   - хранение состояния в PostgreSQL;
   - проверку факта просмотра рекламы и факта оплаты подписки;
   - REST API для Android-приложения и для тг-бота (внутренний, авторизованный).
3. **PostgreSQL** — единый источник правды: пользователи, ноды, инбаунды/клиенты
   (зеркало состояния 3x-ui), подписки, платежи, просмотры рекламы, алерты,
   настройки (цена подписки, длительности за рекламу, пороги алертов).
4. **Android-приложение** — простой UI (одна кнопка «подключить», выбор времени
   через рекламу или подписку), без выбора сервера/страны, интеграция с
   VPN-конфигом (VLESS URI) и с рекламным SDK (РСЯ, rewarded video).
5. **Telegram-бот** — два режима (пользователь/админ), оплата в крипте,
   поддержка, полная админка нод и параметров сервиса без доступа к серверу
   напрямую.

## 2. Этапы разработки

**Этап 0 — R&D и контракты API (перед кодом)**
- Поднять тестовый стенд: 1 нода (3x-ui) + локальный вызов API, проверить
  какие операции требуют сессионную куку, а какие — Bearer/API-токен.
  Здесь стоит уточнить: авторизация 3x-ui — по логину/паролю панели.
- Зафиксировать формат конфигурации, которую получает клиент (VLESS URI/JSON),
  чтобы Android-приложение и главный сервер использовали единый контракт.
- Спроектировать схему PostgreSQL (users, subscriptions, nodes, node_credentials,
  clients, ad_views, payments, alerts, settings, admin_audit_log).

**Этап 1 — Главный сервер: ядро + управление нодами**
- [x] CRUD нод (добавление/удаление/смена пароля — из тг-админки).
- [x] Установка 3x-ui на чистый Ubuntu-сервер по SSH (`asyncssh`), с
  собственными админ-креды панели (не доверяем автогенерации 3x-ui) —
  кнопка «Ноды → Добавить ноду» в боте доводит ноду от «голого»
  VPS до раздающей VPN за один вызов (SSH-бутстрап → создание ноды →
  провижининг инбаунда). Версия 3x-ui запинена константой (см. риск ниже).
  SSH-пароль не сохраняется нигде, только транзитно; сообщение с ним бот
  сразу удаляет из чата. **Не проверено на реальном VPS** — сама
  SSH-оркестровка (порядок команд, обработка ошибок/таймаутов) протестирована
  локально против фейкового SSH-сервера, но команды `install.sh`/
  `x-ui setting` взяты из документации 3x-ui, а не с живого прогона.
- [x] Создание инбаунда + автоподбор SNI (проверка кандидатов реальным TLS
  1.3-хендшейком).
- [x] Создание/удаление клиентов на существующем инбаунде.
- [x] Функция смены SNI по кнопке из тг-бота (карточка ноды → «Сменить SNI») — ключевая пара
  сохраняется, старые VLESS-конфиги для ноды перестают работать (это
  неизбежное следствие смены SNI в REALITY, не баг).

**Этап 2 — Мониторинг и балансировка**
- [x] Heartbeat/health-check нод (`get_online_clients`, таймауты, consecutive-failure счётчик).
- [x] Alerting с настраиваемым порогом → уведомление в тг админу (сервер шлёт
  напрямую через Telegram Bot HTTP API, не завися от того, жив ли процесс бота).
- [x] Балансировщик: при выдаче клиента — реальная нагрузка (только активные
  клиенты) + оценка связи (реальный пинг от клиента, либо грубая оценка по
  стране через `CF-IPCountry`).
- [x] Функция переброса пользователя с одной ноды на другую («Клиенты →
  Перенести клиента» в боте, `POST /clients/{id}/migrate` на
  сервере): создаёт клиента на новой ноде с тем же оставшимся сроком
  действия, удаляет со старой, обновляет `Client.inbound_id`/UUID/email,
  возвращает новый VLESS-конфиг. Порядок специально "создать новое → удалить
  старое", чтобы неудачное удаление на нездоровой ноде не оставило
  пользователя без доступа. Проверено на двух нодах end-to-end.

**Этап 3 — Telegram-бот, MVP**
- [x] Пользовательская часть: `/subscribe` (CryptoBot), `/support` (форвард
  админам через FSM-диалог "опишите проблему одним сообщением").
- [x] Админ-часть: ноды (добавить/бутстрап по SSH/список/провижининг/смена
  SNI/удаление), настройки (цена, длительности рекламы, порог алертов,
  длительность подписки — раздел «Настройки» в админ-панели), всё пишется в
  `admin_audit_log`.
- [x] Переброс пользователей между нодами из бота («Клиенты», см. Этап 2).
- [x] Выдача админских VPN-конфигов с явным выбором сервера («Клиенты →
  Выдать конфиг»: бот спрашивает Telegram ID и часы, а ноду админ выбирает
  кнопкой из списка). Единственный путь, где балансировщик сознательно
  обходится; обычным пользователям выбор ноды по-прежнему не показывается.
- [x] Интеграция с CryptoBot: создание инвойса, ручная проверка «Я оплатил»,
  и реальный вебхук (см. Этап 6) — оплата зачисляется автоматически, без
  клика пользователя.
- [x] Весь интерфейс бота — на инлайн-кнопках, у пользователя и у админа.
  Команд запоминать не нужно: `/start` открывает меню, дальше всё тапами.
  Там, где без ввода не обойтись (IP ноды, пароль, цена), бот ведёт
  пошаговый диалог — по одному значению за шаг, с примером в подсказке,
  валидацией (IP, целые числа) и кнопкой «Отмена» на каждом шаге. Сообщения
  с секретами (root-пароль, токены) бот удаляет из чата сразу после
  прочтения. Мастер редактирует одно и то же сообщение-панель, а не
  засыпает чат новыми.
  - Проверено прогоном синтетических Telegram-апдейтов через настоящий
    Dispatcher (41 проверка): маршрутизация, переходы FSM, отсев не-админов
    от админских кнопок, валидация неверного IP, удаление сообщений с
    секретами, конвертация «дни → секунды», возврат «Отмены» в нужный
    раздел, форвард обращения в поддержку.

**Этап 4 — Android-приложение, MVP**
- Экран подключения (кнопка + выбор времени по рекламе).
- Интеграция rewarded-ad SDK (РСЯ): короткая (15 мин) / длинная без перемотки (1ч).
- Экран подписки: сверка цены с главным сервером, флоу авторизации через
  Telegram (deep link + callback), fallback-флоу «нет тг → 15 мин по рекламе → тг».
- Обработка «кнопка VPN не работает»: логирование неудачных попыток подключения,
  запрос альтернативного конфига у главного сервера.
- Локальный VPN-клиент: интеграция xray-core/v2ray core под Android (например,
  через существующие open-source VLESS/Reality Android клиенты как базу) —
  требует отдельного решения по SDK/библиотеке (см. вопросы).

**Этап 5 — Реклама и монетизация**
- Интеграция с рекламной сетью (РСЯ/Yandex Mobile Ads) — rewarded video.
- Учёт просмотров рекламы на сервере (защита от подмены/повторной отправки
  одного и того же ad-impression).
- Логика начисления времени VPN за просмотр.

**Этап 6 — Оплата и верификация через Telegram**
- [ ] Флоу «работает/не работает тг» — это часть Android-приложения (Этап 4),
  не сервера; там же и остаётся, ещё не сделано.
- [x] Криптоплатежи в боте: инвойс → **реальный вебхук CryptoBot**
  (`POST /webhooks/cryptobot`, HMAC-SHA256 по схеме Crypto Pay API,
  `payload`-поле инвойса несёт `telegram_id:plan_code`) → выдача конфига.
  Проверено на подделанной/валидной подписи локально.
- [x] Anti-fraud: платёж идемпотентен по `provider_invoice_id` (повторная
  доставка вебхука или гонка с ручным «Я оплатил» не выдают второй конфиг —
  проверено), ad-view идемпотентен по `provider_impression_id` (было раньше).
- [x] Токен CryptoBot настраивается из бота: «Настройки → Токен CryptoBot» —
  хранится в `settings` зашифрованным, боту виден в открытом виде (нужен
  для реальных вызовов CryptoBot API), в обзоре «Настройки» —
  замаскирован (`(set)`/`(not set)`), сообщение с самим токеном бот сразу
  стирает из чата. Проверено: маскировка, шифрование в БД, точечное чтение
  реального значения, верификация подписи вебхука по значению из БД.

**Этап 7 — Безопасность и отказоустойчивость**
- [ ] mTLS или подписанные запросы между ботом и главным сервером — сейчас
  общий секрет (`X-API-Key`), что приемлемо как база, но не mTLS/подпись
  запроса; для Android-приложения публичный API ещё не спроектирован вовсе
  (см. открытые вопросы). Осталось не сделано.
- [ ] Ротация паролей/токенов нод — SSH-бутстрап генерирует свои креды
  панели один раз при установке, но команды на их последующую смену/ротацию
  нет (была бы нужна повторная SSH-сессия или API 3x-ui, если он это умеет —
  не проверено). Осталось не сделано.
- [x] Аудит действий админа — `admin_audit_log` пишется на каждое
  мутирующее действие (ноды, настройки, миграция клиента, выдача
  админского конфига), не только на смену настроек.
- [x] Резервное копирование PostgreSQL: `scripts/backup_postgres.sh`
  (pg_dump → gzip → опционально S3, ротация локальных копий по возрасту) —
  проверено round-trip (dump → restore на реальном Postgres, данные целы).
  План восстановления нод как таковой не написан (это, по сути, повторный
  «Добавить ноду» — нода не хранит состояния, которое нужно было бы
  восстанавливать, кроме самой БД).
- [x] Rate-limiting: Redis-based fixed-window лимитер поверх
  Cloudflare-защиты — на выдачу клиента (10/час на telegram_id), ad-view
  (20/час на telegram_id) и вебхук CryptoBot (60/мин на IP). Проверено на
  реальном Redis (лимит срабатывает, окно корректно истекает).
- [x] `install.sh` — установка главного сервера на чистую машину одним
  запуском: ставит Docker, генерирует `.env` (реальные секреты сам, у
  админа спрашивает только токен бота и админские telegram id — цена,
  длительности рекламы и токен CryptoBot настраиваются позже из бота, не
  здесь), поднимает Postgres/Redis, прогоняет Alembic-миграции с хоста
  (не из контейнера — `migrations/env.py` резолвит `../server`
  относительно себя на диске, что работает только снаружи образа
  сервера), затем собирает и поднимает server/worker/bot. Идемпотентен —
  повторный запуск не трогает существующий `.env` и не ломает уже
  накаченные миграции.
  - Проверено в этом окружении: генерация `.env` (секреты, отсутствие
    незаполненных плейсхолдеров) и сам механизм миграций (venv на хосте +
    подмена `@db:` на `@localhost:` + `alembic upgrade head`, дважды подряд
    — идемпотентно) на реальном Postgres. Часть с Docker Compose
    (`docker compose up`) не проверена вживую — в этой песочнице нет
    доступа к демону Docker (`dockerd` не поднимается), нужна проверка на
    реальном сервере перед первым боевым использованием.
  - Доработан под «чистую Ubuntu» после реального прогона на VPS, где он
    упал: `python3 -m venv` на Debian/Ubuntu требует отдельного пакета
    `python3-venv`, без него шаг миграций падал с «ensurepip is not
    available». Теперь скрипт доустанавливает базовые пакеты (curl,
    ca-certificates, python3) и venv-поддержку сам, выводя имя пакета из
    версии установленного интерпретатора (`python3.14-venv`) с откатом на
    generic `python3-venv`. Заодно убрана зависимость от библиотеки
    `cryptography` на хосте: Fernet-ключ — это 32 случайных байта в
    base64url, генерируется stdlib (проверено, что настоящий `Fernet`
    такой ключ принимает и данные на нём шифруются/расшифровываются).
    Ожидание готовности Postgres читает health-статус прямо из
    `docker inspect`, а не парсит вывод `docker compose ps`, формат
    которого отличается от версии к версии.
  - Проверено: реальный запуск на этой машине проходит секции 1–2 и
    останавливается на недоступном демоне Docker с внятным сообщением, не
    оставив недописанный `.env`; ветка «нет ensurepip» протестирована через
    PATH-подмену `python3`/`apt-get` — ставит `python3.14-venv`, при его
    отсутствии откатывается на `python3-venv`, а когда нет ни того ни
    другого (или падает сам `apt-get update`) — сообщает, что именно
    поставить руками, вместо голого кода выхода.
- [x] Подключение Cloudflare — двумя путями:
  - **Из бота** (основной путь, чтобы не нужен был shell-доступ к серверу):
    «Cloudflare → API-токен» и «Zone ID» (задаются
    один раз, токен хранится зашифрованным, как токен CryptoBot), затем
    «Cloudflare → Подключить домен» (бот спросит домен и IP) — создаёт/обновляет
    проксированную A-запись через Cloudflare API v4 (идемпотентно) и
    выставляет SSL-режим `full`; IP сервера, если не указан, определяется
    автоматически. Делает только DNS/SSL — часть с блокировкой файрвола
    (ниже) отсюда недоступна: код бота/сервера работает внутри контейнера,
    а `ufw` из контейнера не увидит и не изменит файрвол хост-машины.
    Проверено на реальном Postgres: «не настроено» → чистый 400; при
    заданных (тестовых) токене/зоне и недоступной сети (так и есть в этой
    песочнице — прокси блокирует `api.cloudflare.com`) → чистый 502, а не
    500 (после фикса — изначально ветка с авто-определением IP этот
    502-фикс не подхватывала, поймал и поправил на тестах); в
    `admin_audit_log` не остаётся мусора при неудачной попытке.
  - **`scripts/setup_cloudflare.sh`** — тот же результат (DNS + SSL) с хоста
    напрямую, плюс опциональная (`--lock-firewall`, с явным подтверждением)
    блокировка 80/443 в ufw только для IP-диапазонов Cloudflare — то, что
    бот сделать не может. Не трогает SSH и не удаляет существующие правила
    автоматически — обзор и чистка оставлены администратору, чтобы не
    рисковать потерей доступа к серверу.
  - Сами вызовы Cloudflare API не проверены живьём ни там, ни там —
    сетевая политика этой песочницы блокирует `api.cloudflare.com` на
    уровне прокси (не связано с кодом); нужен реальный токен/домен для
    сквозной проверки.

**Этап 8 — Тестирование и запуск**
- Нагрузочное тестирование балансировки трафика.
- Пилотный запуск на 2–3 нодах, мониторинг реальных алертов.
- Постепенный вывод в прод.

## 3. Технологический стек (зафиксировано)

- Главный сервер: Python, FastAPI — REST API + оркестрация 3x-ui API нод.
- БД: PostgreSQL (задано в README) + Alembic для миграций, SQLAlchemy/SQLModel
  как ORM.
- Тг-бот: Python, aiogram — отдельный сервис, ходит во внутренний API главного
  сервера (не в БД напрямую).
- Секреты нод (логин/пароль панели 3x-ui) — хранить в PostgreSQL в
  зашифрованном виде (например Fernet/pgcrypto), ключ шифрования — вне БД.
- Android: Kotlin, интеграция xray-core через **AndroidLibXrayLite**
  (2dust/AndroidLibXrayLite) — gomobile-AAR той же кодовой базы xray-core, что
  используется на нодах (через 3x-ui). Выбрана вместо sing-box mobile именно
  из-за гарантии протокольной совместимости REALITY/XTLS-vision между
  клиентом и сервером — сервер жёстко завязан на xray-core, и независимая
  реализация (sing-box) несёт риск расхождений в edge-кейсах (short_id,
  spiderX, vision flow).
- Мониторинг: Prometheus/Grafana или встроенные метрики + алерты в тг.

Предлагаемая структура монорепозитория:
```
VPN-3X/
├── server/          # FastAPI: API, оркестрация нод, балансировка, БД-модели
├── bot/             # aiogram: пользовательский и админ-бот
├── android/         # Kotlin-приложение (появится на этапе 4)
├── migrations/       # Alembic-миграции PostgreSQL
└── PLAN.md
```

## 4. Принятые решения

1. **Репозиторий**: весь код (главный сервер, тг-бот, позже Android)
   разрабатывается с нуля в этом репозитории `VPN-3X`, монорепозиторий.
2. **Стек главного сервера и тг-бота**: Python — FastAPI для главного сервера
   (REST API + оркестрация нод), aiogram для тг-бота. Общий внутренний
   клиент/схемы (pydantic) переиспользуются между сервисами.
3. **Авторизация в 3x-ui на нодах**: главный сервер логинится в панель
   логином/паролем (сессионная кука), а не через API-токен ноды. Значит нужно:
   - хранить логин/пароль каждой ноды в БД в зашифрованном виде;
   - реализовать менеджер сессий (логин → кука → переиспользование → релогин
     при истечении/401);
   - учитывать, что `openapi.json` в v3.6.0 и часть операций требуют именно
     авторизованную сессию, а не токен — значит login-flow обязателен для всех
     операций, а не только вспомогательных.
4. **Криптоплатежи — провайдер: CryptoBot (Crypto Pay API)**. Нативен для
   Telegram, без явных комиссий за приём (доход провайдера — со спреда),
   простой REST API (создание invoice, проверка статуса, вебхуки) — ложится
   на флоу README «бот в тг принимает оплату» напрямую, без отдельного
   мерчант-KYC. Тем не менее модуль оплаты в боте проектируется за
   интерфейсом `PaymentProvider`, чтобы при необходимости добавить
   NOWPayments/Cryptomus как альтернативу (например для юрлица/некастодиальной
   схемы) без переделки остального бота.
   - Нужен API-токен приложения в @CryptoBot (получается через `/pay` →
     Create App в самом боте). Задаётся не через env/деплой, а прямо из
     тг-бота («Настройки → Токен CryptoBot», хранится в таблице `settings`
     зашифрованным тем же Fernet-ключом, что и пароли панелей нод) — можно
     добавить или сменить в любой момент без передеплоя.
   - Webhook от CryptoBot подписывается и верифицируется на стороне
     главного сервера (проверка подписи запроса по этому же токену) перед
     зачислением подписки.
5. **Реклама — Yandex Mobile Ads SDK** (официальный SDK РСЯ для Android,
   формат Rewarded video). Различие «15 мин — короткая / 1ч — длинная без
   перемотки» реализуется на нашей стороне (наше приложение решает, какой ad
   unit показывать и включает non-skippable плеер там, где SDK это позволяет),
   сам показ и начисление события идёт через стандартный rewarded-callback SDK.
   - Нужен аккаунт в Yandex Partner (partner.yandex.ru) и ad unit ID для
     rewarded-формата — потребуется от заказчика перед этапом 5.
6. **Android VLESS-библиотека — AndroidLibXrayLite** (см. раздел 3) — тот же
   xray-core, что и на нодах, минимальный риск протокольного рассинхрона.

7. **Дистрибуция — Google Play.** Значит: приложение позиционируется как
   обычный VPN-сервис (без формулировок «обход блокировок» в листинге),
   обязательна политика конфиденциальности, декларация VPN-разрешения
   (`BIND_VPN_SERVICE`) и прохождение проверки на семейственность с
   политиками Google по прокси/VPN-приложениям — закладываем это в этап 4
   как отдельный чек-лист перед публикацией.
8. **Масштаб — целимся в большое число пользователей и близкую к
   безотказной работу.** Точные цифры ещё не заданы, но это фиксирует
   архитектурный принцип: с первого дня строим сервис так, будто он уже
   большой, а не мигрируем на это потом. Конкретные вытекающие решения — в
   разделе 6.

## 6. Архитектура для высокой доступности и масштаба

Так как цель — большое число пользователей и «почти безотказно», часть решений
зафиксирована сразу, чтобы не переделывать позже:

- **Главный сервер — stateless.** Любое количество инстансов FastAPI за
  балансировщиком/Cloudflare; вся сессия/состояние — в PostgreSQL и Redis, не
  в памяти процесса.
- **Асинхронный стек**: FastAPI + SQLAlchemy 2.0 (async) + asyncpg + пул
  соединений; в проде — pgbouncer перед PostgreSQL, чтобы не упереться в
  лимит соединений при масштабировании подов.
- **Фоновые задачи отделены от запросов**: health-check нод, автоподбор SNI,
  ре-баланс трафика — не в теле HTTP-запроса, а в отдельном воркере (очередь
  на Redis, `arq`). Это значит, что зависший/недоступный узел не блокирует
  API и не роняет запросы пользователей.
- **На каждую ноду — таймауты + retry + circuit breaker** в клиенте 3x-ui API,
  чтобы одна нестабильная нода не деградировала весь сервис.
- **Идемпотентность на границах**: подтверждение оплаты (CryptoBot webhook) и
  начисление времени за рекламу должны обрабатываться идемпотентно (по
  invoice_id / ad-impression-id), чтобы повторная доставка вебхука или ретрай
  с Android не начислял VPN дважды.
- **Миграции БД — expand/contract**, без блокирующих `ALTER` на больших
  таблицах, чтобы рас-катка новой версии не требовала даунтайма.
- **Graceful shutdown** и readiness/liveness health-checks с первого дня —
  чтобы rolling deploy не ронял активные подключения.
- Нагрузочное тестирование балансировки (уже было в этапе 8) — делать не в
  конце, а по мере роста числа нод, чтобы не упереться в лимиты неожиданно.

## 7. Риски

- Автоподбор «рабочего» SNI для REALITY нестабилен во времени (блокировки
  провайдеров меняются) — нужен регулярный фоновый ре-чек, а не разовая проверка.
- 3x-ui `openapi.json` теперь требует сессию — обновления библиотеки/API 3x-ui
  могут внезапно ломать интеграцию главного сервера, нужен pin версии + CI-тест
  на реальном стенде при апдейте нод.
- Anti-fraud для рекламы и крипто-оплаты — обязательное условие, иначе сервис
  легко эксплуатировать (бесконечный VPN без оплаты).
- 2GB RAM на ноде — ограничение по количеству одновременных клиентов/трафика,
  нужно заложить лимиты в балансировщик заранее.
